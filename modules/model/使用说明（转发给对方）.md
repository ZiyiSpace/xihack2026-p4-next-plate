# Jev-Omni 菜品识别接口 · 使用说明

**这个接口只做一件事：认菜名。**

给它一张菜品照片 + 一份候选菜名清单，它告诉你这是哪一道菜，以及每一项的概率。

同一个模型另外提供一个通用的「一句话问题 + 候选答案」入口（`/v1/ask`），需要时可以用。

---

## 这是什么（模型）

一个**多模态决策分类接口**。给它一段情境、一个问题、若干候选选项，它返回每个选项的概率。

它**不是聊天模型**：不生成文字，只输出概率分布，一次请求一次前向，速度快（通常 0.3–1.1 秒）。

支持的输入模态：**文本 / 图片 / 音频 / 视频**。

因为它只会"从给定选项里挑一个"，所以任何用途都得写成**一句话问题 + 候选答案**。

## 快速开始

### 网页版（推荐先试这个）

浏览器打开：

```
https://u1201184-80c0-dda3c400.westb.seetacloud.com:8443/ui
```

把密钥粘进最上面的「API Key」框（只存在你自己的浏览器里），然后：

- **① 菜品识别** —— 选一张菜品照片，下面把候选菜名一行一个填好（填你店里实际有的菜），点「开始识别」。
- **② 通用提问** —— 自己写一个问题加几个候选答案，需要就带一张图，点「提问」。

### 菜品识别（代码调用）

先存一份候选菜名清单，之后调用只传清单名字：

```bash
URL=https://u1201184-80c0-dda3c400.westb.seetacloud.com:8443
KEY=PASTE_YOUR_KEY_HERE

curl -s -X POST "$URL/v1/menu" \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"name":"本店菜单","items":["红烧肉","小笼包","宫保鸡丁","麻婆豆腐","扬州炒饭"]}'
```

再传照片识别：

```bash
curl -s -X POST "$URL/v1/identify" \
  -H "Authorization: Bearer $KEY" \
  -F "menu=本店菜单" -F "file=@dish.jpg"
```

返回：

```json
{
  "dish": "麻婆豆腐",
  "confidence": 0.997,
  "margin": 0.996,
  "abstained": false,
  "ranking": [
    {"option": "麻婆豆腐", "probability": 0.997},
    {"option": "宫保鸡丁", "probability": 0.001}
  ],
  "latency_ms": 274
}
```

`confidence` 就是「它有多确定」。**低于 0.6 建议当作没认出来**，别硬用。

### 通用提问（任意其它用途）

模型**不会自由生成文字**，只会从你给的选项里挑一个。所以任何新用途都是「一句话问题 + 候选答案」：

```bash
curl -s -X POST "$URL/v1/ask" \
  -H "Authorization: Bearer $KEY" \
  -F "question=这盘菜吃完了吗？" \
  -F $'options=吃完了\n还剩一半\n几乎没动' \
  -F "modality=image" -F "file=@plate.jpg"
```

不带 `options` 时默认 `是` / `否`；`modality` 可以是 `text` / `image` / `audio` / `video`。

### 最简单的例子（文本）

```bash
curl -s -X POST https://u1201184-80c0-dda3c400.westb.seetacloud.com:8443/v1/decide \
  -H "Authorization: Bearer PASTE_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "state": "会议 10 点开始，现在是 9 点。",
    "question": "会议开始了吗？",
    "options": ["是", "否"]
  }'
```

返回：

```json
{
  "prediction": "否",
  "prediction_index": 1,
  "confidence": 0.999301,
  "probabilities": { "是": 0.000699, "否": 0.999301 },
  "modality": "text",
  "latency_ms": 261.1
}
```

- `prediction` — 概率最高的选项
- `confidence` — 该选项的概率
- `probabilities` — 所有选项的完整概率分布（可自己设阈值决定「不确定」）

## `POST /v1/identify` 参数

| 字段 | 必填 | 说明 |
|---|---|---|
| `file` | 是 | 菜品照片 |
| `menu` | 二选一 | `/v1/menu` 存好的清单名 |
| `options` | 二选一 | 或内联候选菜名，每行一个 |

| `question` / `state` | 否 | 一般不用改 |

## 菜品识别有多准（真实照片实测）

拿维基百科的真实菜品照片测的：8 张目标菜 + 1 张咖啡（不在清单里的干扰项）。

| 候选清单规模 | 正确率 |
|---|---|
| **8 道菜** | **8/8 = 100%**（置信度 0.91–0.998） |
| 12 道（掺了饺子、馄饨等相似菜） | 7/8 = 87.5% |
| **40 道菜**（真实菜单规模） | **6/8 = 75%** |
| 40 道 + 「以上都不是」 | 7/8 = 87.5% |

**置信度能当过滤器用**：40 道那组里，置信度 ≥ 0.78 的 5 张全对；置信度 < 0.40 的只对了 1/3。

三条件建议：

1. **候选清单越短越准**。8 道 100%，40 道 75%。菜多就先分档（肉类 / 蔬菜 / 主食 / 点心）再在档内选。
2. **置信度低于 0.6 就当没认出来**，转人工，或缩小清单重试。
3. 会错的基本都是**长得像的菜**（饺子↔馄饨、糖醋里脊↔宫保鸡丁），加长清单救不回来。

## 输入限制

| 项目 | 限制 |
|---|---|
| 选项数量 | 2–256 个；**超过 20 个质量明显下降**（实测：8 道 100%、40 道 75%） |
| 音频时长 | 最长 30 秒，超出部分会被截断 |
| 视频 | 固定抽取 16 帧 |
| 上传文件 | 单个最大 200 MB |
| 支持格式 | 图片、音频、视频常见格式均可（内部用 ffmpeg / OpenCV 解码） |
| 并发 | 单张 GPU 串行推理，**请勿高并发**；并发请求会自动排队，不会失败但会变慢 |

## 使用建议

- **先看 `/docs` 或 `/ui`**，在上面直接试几条再写代码，最省时间。
- **候选清单越短越准**：8 道菜 100%，40 道菜 75%。菜多就先分档（肉类 / 蔬菜 / 主食 / 点心）再在档内选。
- **置信度低于 0.6 就当没认出来**，转人工或缩小清单重试。
- **用 `probabilities` 而不是只看 `prediction`**：菜品识别里它很有信息，阈值可以自己定。
- **`state` 写清楚上下文**：模型只看你给的情境，它没有记忆，每次请求都是独立的。
- **选项表述保持平行**：例如都写成「是/否」「正面/中性/负面」，不要混着写不同粒度的描述。
- **不要并发轰炸**：需要批量处理时请串行或小并发（2–3），否则大家都会变慢。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| `401` | 密钥缺失或错误，检查请求头 |
| `422` | 参数不合法，例如只给了 1 个选项，或 `modality=image` 但没传文件 |
| `413` | 上传文件超过 200 MB |
| `503 model is still loading` | 服务刚重启，模型正在载入，约 40 秒后可用 |
| 请求很慢 | 可能有人在并发调用，排队中；或视频输入（约 1 秒） |
| 音频报错 | 音频需能正常解码，请确认文件本身可播放 |
