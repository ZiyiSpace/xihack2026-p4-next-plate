## 一、结论摘要

依赖图**无环**，`core` 不 import 任何上层，没有真正的反向依赖。问题集中在两类：

1. **同一件事有多份实现**（耦合的另一种形式）：时间格式化 3 份、判读分类中文说法 2 份、
   克数格式化 2 份、判读分类取值 **7 处事实来源**、图片引用→存储 key 的推导 2 份、
   两个 CDP 脚本约 60 行样板重复。
2. **少数函数承担过多职责**：`adapter.build_view` 167 行 / 43 个分支 / 8 件事；
   `core.ingest_station_event` 111 行；`adapter.attach` 98 行。

审查过程中实证出 **6 个真 bug**，其中 2 个是既有代码的，都已修。

## 二、修掉的（每条都有实测证据）

### 1. 既有 bug：工作台「待补充」数量常年翻倍

`analytics.dish_summaries` 里有两段**逐字相同**的在途量累加（原 `analytics.py:143-147` 与 `163-166`），
在售菜品被加了两遍。

```
修复前：任务 quantity_g=50（折合 2 个）  →  工作台「待补充」显示 4 个
修复后：任务 quantity_g=50（折合 2 个）  →  工作台「待补充」显示 2 个
```

这不是显示问题：后厨按「待补充 4 个」备料，实际只有 2 个在途。
修法是删掉前一段，把唯一的累加放到「补全菜品」之后——这样既不会重复，
也能覆盖「已撤盘但仍有未完成补菜任务」的菜品。

### 2. 样例的 PATCH 接口不校验，脏数据能一路存到入账时才炸

原来收的是裸 `dict`。实测：

```
修复前：PATCH observed_at="garbage" -> 200（照单全收）
        POST  /api/samples/ingest    -> 500
修复后：observed_at 非法/无时区 -> 422    dish_id 不存在 -> 422    net_weight_g=-5 -> 422
        net_weight_g="" -> 200（清空读数，不是 0）
```

### 3. 批次中途出错 → 数据库和登记状态对不上

`_ingest` 的循环没有单条隔离，一条抛错就整批中断，`_save` 走不到。实测：

```
修复前：ingest -> 500
        样例状态 ['pending','pending']   ← 第一条明明已经入账了
        工作台却已有账：小馒头 201g，1 张抓拍        ← 两边不一致

修复后：ingest -> 200，ingested=1 failed=1
        样例状态 ['done','failed']       ← 每条都被记住
```

仓内既有约定本来就是「单条失败不阻断批次」（`adapter.api_ingest`），这次是补齐一致性。

### 4. 自动分盘会和手填盘号撞车

`used` 只查 `servings`，手填的盘号因为 `continue` 不进集合。全新库上
「有人填了 P001 + 另一道菜留空」会把 P001 再发一次，两道菜混进同一个 serving。
修法：手填盘号也先占位。

### 5. 改完输入再点运行，会显示「已入账」但结果是空的

事件按 `event_id` 幂等，重复上报被忽略，返回里既没有 `interpretation` 也没有 `error`，
于是被判成 `done` 且结果全空。现在如实说明：
「这条样例已按编号入账过，本次上报被幂等忽略；改动要用『复位并重跑』才会生效」，
并在界面上补了**「复位并重跑」**按钮。

### 6. 样例登记表借用了通用 `meta` 表

`db.reset_all()` 会整表清空 `meta`，于是「复位业务数据」会**顺手删掉用户上传的样例**——
而改完输入想重算时，正需要这些样例还在。已改成 `data/samples.json` 独立存放。实测：

```
复位前 2 条 -> 复位后 2 条（样例保住）    工作台菜品 -> 空（业务数据确实清了）
```

同时给读-改-写整体加了锁：`db` 的锁只保护单条 SQL，跨不过「取快照 → 整表覆盖」，
而 `api_create` 是 `async def`、`_load` 与 `_save` 之间还有 `await f.read()`，
并发上传/编辑会互相整批覆盖。

### 7. 同一件事的多份实现

| 重复内容 | 原来几份 | 现在 |
|---|---|---|
| 时刻格式化 `HH:MM` | **3**（`capture-card` / `sample-intake` / `workspace`） | 1（`lib/reading.ts`） |
| 判读分类中文说法 | **2**（内容一致但无约束） | 1 |
| 克数格式化 | 2（一个有 null 处理一个没有） | 1 |
| 图片引用 → 存储 key | 2（`samples._read_bytes` / `adapter._image_url`） | 1（`images.key_of`） |
| 两个 CDP 脚本的样板 | ~60 行 | **未修**（见下） |

### 8. 顺带修掉的

- **`capture-card` 把正常流转画成黄色告警**：`classificationTone[...]||"watch"` 让没配色的
  分类一律回落到 `watch`，于是「首次上盘基准」「无明显变化」都带警告底色。改成中性默认。
- **`adapter` 手写 SQL 查事件**，而别处都用 `db`：新增 `db.get_recent_captures()`。
- **`sample-intake` 的 `send()` 返回类型是假的**（用 `as unknown as` 硬转）：改成泛型。
- **契约文档与实际不符**：`schemas.InterpretationResult` 列了**从来不产出**的 `mismatch`
  （`refill.py` 里那个 `mismatch` 是局部变量名），却漏了实际会产出的
  `out_of_order` 与 `no_weight`。已按 `interpreter` + `core` 的真实产出改正。
