### 顺带查出的一个既有 bug：`_post` 的重试白名单从来没生效

原 `_post` 是这么写的：

```python
try:
    ...
    if r.status_code in (401, 422, 413):
        r.raise_for_status()          # ← 这一抛是在 try 里面的
    ...
except (httpx.HTTPError, JevUnavailable) as e:   # ← HTTPStatusError 是 HTTPError 的子类
    last_err = e                                  # ← 于是又被抓住，照样重试
```

**`raise_for_status()` 抛的 `HTTPStatusError` 是 `httpx.HTTPError` 的子类**，所以它立刻被同一个
`except` 抓住，进入下一轮重试。文档里写的「401/422/413 不重试」**从来没有生效过** ——
错误密钥、404、422 全都会老老实实重试三次。

**已修**：把状态码判断移出 `try`，只重试「可能自己好的错误」（transport 异常、5xx、
408/425/429，以及**该端点应当存在时**的 404）。其余 4xx 立即抛 `JevUnavailable`。

实测：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| `/v1/portion`（端点不存在） | 24.9 s（3 次请求） | **8.4 s（1 次请求）** |
| `/v1/measure`（端点不存在） | 30.5 s（3 次请求） | **10.1 s（1 次请求）** |
| 错误密钥 → 401 | ≥10.5 s（纯退避）+ 3 次往返 | **4.7 s（1 次往返）** |

服务器侧计数确认：调一次 `/v1/portion`，`api.log` 里 `POST /v1/portion` **只 +1**（107 → 108）。

## 七、候选清单规模实测（该给模型几个选项）

**起因**：有人问「你到底给了模型几个选项」，怀疑选项太少会让识别变成走过场。

**先说清事实**：`vision.identify_dish` 传的是**库里的全部菜品**，不是这一盘绑定的那道菜。
当前库里 6 道（小馒头、南瓜饼、鱼丸、豆腐片、腌牛肉、腌鸡肉），服务端返回的是
**整份概率分布**（`dish` / `confidence` / `margin` / `abstained` / `ranking`），
我们取 argmax 并卡 0.6 的置信度下限。

**然后实测**。`measure_identify_options.py` 拿 v0.2 数据集的 20 张图，按三档各跑一遍。
真值取自 `image_manifest.json` 的 `prompt_key` 前缀（`bun_*`=小馒头、`beef_*`=腌牛肉），
不是从模型输出反推的。`*_empty` 是**空盘**（盘上没菜），对空盘问「这是哪道菜」本身就是
畸形问题，所以分开统计：空盘答「拒答」才算对，高分报出菜名算**编造**。

| 候选清单 | 有菜图（14 张） | 空盘图（6 张） | 合计 |
|---|---|---|---|
| 2 项（只给本批出现过的两道菜） | **14/14** | 1/6 | 15/20 |
| 6 项（完整菜品目录） | 13/14 | 3/6 | 16/20 |
| 6 项 +「以上都不是」 | 10/14 | **5/6** | 15/20 |

**结论与服务方的《使用说明》一致，而且方向跟直觉相反**：

1. **选项越多越不准。** 2 项 14/14 全对，6 项掉到 13/14，唯一错的是 M005
   （腌牛肉 → 豆腐片 0.945，**高置信误判**）。服务方自己测的是 8 道 100%、40 道 75%，
   「候选清单越短越准」「超过 20 个质量明显下降」。
2. **「以上都不是」会误伤真的菜。** 服务方提醒过「容易误伤真的菜」，我们的数据坐实了：
   有菜图从 13/14 掉到 10/14，M002/M003/M007 三盘**真的有腌牛肉**却被判 `abstained`。
3. **但空盘上必须给它。** 不给的话模型会用 0.71–0.99 的置信度编一个菜名出来
   （6 张空盘只对 1 张）；给了之后 6 张对 5 张。

所以正确做法不是「多给选项」，而是**先知道盘上有没有菜**。我们本来就有称重：
`vision.identify_dish(plate_has_food=...)` 只在净重不超过噪声界时追加「以上都不是」，
有菜就按短清单走。改动见 `samples.py::_identify`。

明细：`evidence/候选清单规模实测.json`、`evidence/候选清单规模实测-摘要.txt`。

## 九、改动自查（高内聚低耦合）

按「改动是不是各就各位」又过了一遍自己的 diff，逐条都是实测出来的，不是读代码猜的。

### 1. 崩页 bug：非补菜任务的分量是 null（最严重）

新增 `replace` 动作后，**后厨页面整页崩了**：`Cannot read properties of null (reading 'toLocaleString')`。
链路是 `workspace.tsx` 的「已结束任务」表格 → `qty(t.quantity)` → `number(null)`。

根因不在新代码里，是**既有隐患被新动作暴露**：`qty()` 一直假定 `quantity` 是数字，
而适配层对非补菜任务给的就是 `null`（换菜/撤盘/巡检都没有分量）。以前 `check`/`pull`
从来没人把它们点成已结束，所以没炸过；我一取消演示单就炸了。

修法不是加个 `?.`，而是把「这条任务的分量怎么说」收成一处
`amountText(t, unit)`，任务卡、已结束任务表、详情弹窗三处共用 —— 原来这段
`action==="replace"?…:…` 的判断散在三处，漏一处就是这个 bug。
验收脚本现在显式断言页面没有运行时错误（`crashed` 字段），别再退回去。

### 2. 升级尺度用错了阈值

```python
"high" if replace_overdue >= config.REPLACE_AFTER_MIN / 2 else "medium"
```
`replace_overdue` 是相对**这道菜自己的**期限算的，尺子却用**全局默认**。配了 150 分钟的菜
超时 50 分钟只是 33%，却因为「50 ≥ 90/2」被判成 high。已改成 `config.replace_after(dish) / 2`，
冒烟用例 5 专门盯这条（修之前会失败）。

### 3. 配置值漏进了接口快照

`serving_metrics` 一度把 `replace_after_min` 一起返回。它是**配置**不是**测量结果**，
而 `core.serving_snapshot` 用 `**m` 把整个字典摊进 `/api/events` 的 serving 快照，
于是配置值就这么进了接口返回，`schemas.ServingSnapshot` 里还没声明它
（顺带暴露：`age_min` 同样没声明，说明这个模型本来就没被用来校验）。
现在只回 `replace_overdue_min` 这个测量结果，配置由调用方问 `config.replace_after(dish)`。

### 4. 「菜品级覆盖 → 全局默认」原本有两份实现

`analytics` 里 `dish.get("freshness_min") or config.FRESHNESS_WINDOW_MIN`，
我照抄了一份给 `replace_after_min`。同一条回退语义两处实现，加第三个字段必然漏。
已收进 `config.freshness_window(dish)` / `config.replace_after(dish)`，注释写明这条规则只在这里。

### 5. 三个平行 Record

`actionText` / `actionStart` / `actionDone` 三个 Record 用同一组键，是同一个概念被拆成三份。
已并成按动作分组的 `actionWording`，并把「换下并上新批次」「整盘换新」这两句
原来内联在三元里的文案也收进去。

### 6. `NOISE_BOUND_G` 被借去当空盘阈值

`samples.py` 用 `NOISE_BOUND_G` 判「盘上有没有菜」。那个常量的含义是
「两次读数之差算不算变化」，和「这一盘还算不算有菜」是两件事，默认值恰好都是 4。
已拆出 `config.EMPTY_PLATE_NET_G`，注释说明为什么不共用一个。
