# 虚拟采集端（无硬件时的数据源）

- 负责人：chujieHong（AI 助手：DeepSeek Harness）
- 状态：**可运行** —— 三个子命令都能直接跑，已产出端到端实测结果

## 为什么需要它

项目面向旋转自助烧烤：相机拍盘 + 称重台读数 → 后端判读 → 补菜策略与人群分析。
手上没有硬件，所以预先生成数据集，再由本模块**扮演相机与称重网关**，
把数据当成「刚刚采集到的」通过 HTTP 推给后端真实接口。

它和后端**没有任何代码依赖**：不 import `app.*`，只用 Python 标准库发请求。
换真硬件时整体替换，后端一行不用改；也可以直接指向别人的部署。

## 它模拟了什么

三条流合并成一条时间轴，按各自时刻发出：

| 流 | 数据来源 | 发到哪 |
|---|---|---|
| 站点观测 | 数据集 `observations.jsonl` + `images/*.png` | `POST /api/events/station`（带图片字节） |
| 操作记录 | 数据集 `operation_log.jsonl`（**可选**） | `POST /api/events/operation` |
| 客流 | 本模块 `data/crowd_evening.json` 客流画像 | `POST /api/analytics/covers` |

图片先经 `POST /api/images` 放进后端图片存储，事件里带 `/api/images/<name>` 引用；
同时仍附带图片字节，后端的视觉绑定校验（Jev 认菜）才会真的跑起来，不是空转。

### 怎么换成自己的数据

**两条路：**

- **不碰文件**：管理端 → 门店设置 → **数据接入** → 选图片 → 逐行填净重 → 点运行。
  这条路由 `modules/backend/app/samples.py`（登记/识别/入账）和
  `modules/frontend/components/workspace/sample-intake.tsx`（界面）承担，
  入账走的同样是 `POST /api/events/station`，所以结果自动进工作台口径。
- **命令行**：复制 [`dataset_template/`](dataset_template/README.md) 整个目录，图丢进 `images/`，
  改 `observations.jsonl`，然后 `python capture.py run --dataset 你的目录`。

两条路的区别只是「谁把数据喂进来」：命令行能批量、能复跑、能交给别人；
管理端上传适合手上有几张图、想立刻看到结果。只有 `observations.jsonl` 是必需的；
`operation_log.jsonl` 缺了会自动按每盘首次观测补一条上盘记录（后端要求盘先有开放绑定
才收站点事件），`dish_catalog.json` 只管后端还不认识的菜品，且**只补不覆盖**，
不会冲掉现场调过的计数规则。

## 怎么跑

```bash
cd modules/simulator

python capture.py seed                      # 只把图放进后端存储
python capture.py run --speed 6             # 完整推一遍（默认 ×30，约 7 秒，太快看不清）
python capture.py check                     # 回读后端，逐项确认数据进去了
```

后端地址默认 `http://127.0.0.1:8000`，用 `--backend` 或环境变量 `CAPTURE_BACKEND` 覆盖。
详细参数见 [`README.md`](README.md)。

## 时间轴的两条规则

**倍速只对观测流定义。** 两条流窗口不一样长（观测 220 秒、客流 4 小时），
所以 `--speed 6` 的意思是「观测流压到 37 秒」，客流曲线**线性铺满同一个 37 秒**，
两条流同时结束。这样做演示时长可预期，也不用给两条流各配一个倍速。
实际耗时会超过这个数：开了图片时每条观测都要等视觉服务器推理，实测 8 条约 40 秒。

**默认把整条时间轴平移到当前时刻（`--shift now`）。** 数据集时间戳是 2026-10-03，
直接发进去，后端会按**真实当前时间**与事件时间作差，算出「几小时没有取用」，
把每一盘都判成滞留需复核。采集端模拟的本来就是「刚刚拍到」，
平移既符合场景，也让后端的时效判断成立。`--shift none` 保留原始时间戳，
用于需要和数据集逐字对齐的核对。

## 和谁对接

| 方向 | 谁 | 什么 |
|---|---|---|
| **依赖** | `modules/backend` | `POST /api/images`、`/api/events/station`、`/api/events/operation`、`/api/analytics/covers`、`POST /api/maintenance/reset`、`GET /api/state` |
| **依赖** | `modules/hotpot_dataset_v0_1` | 观测、操作记录与图片（只读 `observations.jsonl` / `operation_log.jsonl` / `images/`） |
| **依赖** | `modules/model` | 不直接调；后端转发的视觉校验实际打到它 |
| **给** | 全队 | 无硬件时的整条链路数据源；也是「后端接口真的接上了」的可复跑证明 |

刻意**不读** `answer_key.jsonl`：它是评分集，按数据集 README 的规定不能作为输入。

## 没做完的

1. **离店与翻台没有接口落点。** `POST /api/analytics/covers` 只收「到店人数」，
   工作台也只有到店人数与每百客口径。画像文件里的 `dwell_minutes` 目前只是场景说明，
   没有变成任何调用。要真正算翻台率，需要后端新增入座/离店事件，并在工作台给它一个位置。
2. **两条流不是同源时钟。** 观测流只有 8 张图、窗口 3 分半，客流画像覆盖 4 小时晚市；
   现在靠「铺满同一段演示时长」对齐。数据集扩容后应改成按真实时间戳统一驱动。
3. **客流是追加写入。** 观测与操作按 id 幂等，重复跑不会翻倍；客流没有幂等键，
   所以 `run` 默认先调 `POST /api/maintenance/reset` 复位，用 `--keep` 才追加。
