# PR：新增虚拟采集端与抓拍图片链路

**分支**：`feat/virtual-capture`（基于 `main` = `a2c262b`）
**标题建议**：新增虚拟采集端与抓拍图片链路，工作台可显示刚采集到的那盘菜

## 为什么

这个项目要做「相机拍盘 + 称重台读数 → 后端判读 → 补菜策略与人群分析」，
但手上没有硬件。已有的 `POST /api/replay` 是**进程内直调 service**的自检回放，
不是设备侧的东西：它绕过了 HTTP，也没法交给别人跑，更不能证明接口真的通。
另外图片只写盘、**没有任何 HTTP 出口**，前端完全拿不到采集画面。

这个 PR 补上「设备那一侧」这个缺失的角色，并让图片真正可读。

| 提交 | 做了什么 |
|---|---|
| `73ae353` 后端 | 新增 `modules/backend/app/images.py`（上传/读取/列目录），事件的 `image_ref` 从宿主绝对路径改成同源 URL；`adapter` 暴露 `captures`；加维护用复位接口 |

## 虚拟采集端是什么

站在**设备那一侧**，只走 HTTP，**不 import 后端任何代码**，只用 Python 标准库。
换真硬件时整体替换，后端一行不用改；也能直接指向别人的部署。

```bash
cd modules/simulator
python capture.py seed    # 把数据集图片放进后端图片存储
python capture.py run     # 按时间轴推送观测、操作与客流
python capture.py check   # 回读后端，逐项确认数据进去了
```

三条流合并成一条时间轴：数据集观测（带图上传）、操作记录、客流画像。
图片先经 `POST /api/images` 落存储，事件带引用；**同时仍附带图片字节**，
后端的视觉绑定校验（Jev 认菜）才会真的跑起来，不是空转。

`check` 不只是数数：它按事件里的 `image_ref` 逐张回取图片，确认状态码与
`Content-Type`，「有引用但取不回」会被直接列出来。

## 顺带修掉的问题

1. **`event_id` 无格式约束却被当文件名** —— 含 `:`、中文或超长的值会被存储拒绝并
   冒泡成 **500**。已在 `schemas.StationEventIn` 加 pattern，非法值在入口就是 422。
2. **`.part` 临时文件会被列目录、被下载** —— 进程被杀后残留的半张图既出现在
   `GET /api/images` 里，也能读出来。改成随机且以前导点开头的名字。
3. **并发写共用同一个临时文件** —— 同名并发上报互相踩踏，后写覆盖前写，
   违反「同名不同内容不覆盖」的契约。已加锁让「查重 + 落盘」成为一个动作。
4. **`image_ref` 存宿主绝对路径** —— `D:\...\data\images\X.png` 对客户端毫无用处。
   改成 `/api/images/<name>`（全仓确认过没有任何代码按路径打开它）。
5. **JPEG 被存成 `.png`** —— `/upload` 不带文件名，落盘统一叫 `.png`，
   读回来 `Content-Type` 就是错的。改为先看文件头再退回后缀。
6. **`ImageStoreError` 是裸 500** —— 已注册处理器：同名冲突 409、名字非法 400。

## 需要 reviewer 注意的一个取舍

**采集端默认把整条时间轴平移到当前时刻（`--shift now`）。**

不这么做的话，数据集时间戳（2026-10-03）进去后，后端拿**真实当前时间**与事件时间作差，
算出「几小时没有取用」，每一盘都显示滞留、状态全是「需复核」——第一次跑就是这样。
平移之后变成「需补充」，这才是这个场景该有的样子。

代价：平移后的终点会落在未来几分钟（播放被压缩了），时段图的小时桶也跟着当前时刻走。
要逐字对齐数据集加 `--shift none`。这条写进了 `模块说明.md`，不是隐藏行为。
