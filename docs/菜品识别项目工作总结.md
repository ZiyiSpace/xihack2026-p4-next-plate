# 菜品识别项目工作总结

更新时间：2026 年 10 月 3 日

## 1. 当前在做什么

你正在为**西安红考拉旋转自助小火锅**开发单店的「补菜与经营分析工作台」。项目从菜品识别与称重数据出发，串联场上余量监控、补菜任务、后厨执行、撤盘报损和经营分析，目标是帮助门店及时补菜、减少浪费，并为经营决策提供数据。

目前已经形成首版原型，主要代码位于 `red-koala/`，界面预览素材位于 `ui-preview/`。根据项目 README，当前以本地运行和更新为主，访问地址为 `http://127.0.0.1:5173/`。

## 3. 当前代码体现的重点

### 厨房端的信息聚焦

厨房端突出工作人员最需要的信息：**补什么菜、补多少、最近一盘何时到达补餐口**。待补菜品按预计到口先后排列，任务汇总和历史记录保留在管理端。

到口倒计时与补菜截止时间独立。真实模式依赖设备上报 `refillArrivalAt`；预测缺失、异常或过期时显示待接入或待更新。模拟模式使用明确标注的 3 分钟转盘周期。

### 识别与称重数据的业务处理

已建立 `/api/ingest` 采集接口，接收盘子生命周期标识、菜品、净重、件数、可信度及撤盘事件，支持设备令牌认证、事件去重和批次原子提交。

同一盘跨圈观测不会重复计入库存；重量下降用于估算取用，重量增加用于推定同盘补充。低可信度、超容量、件数与重量方向矛盾、过期读数等情况会暂停相关自动派单。

**当前应用主要处理上游识别和称重结果，真实视觉识别、称重硬件及采集链路仍待接入。**

### DeepSeek 分析助手

已实现经营问答入口，以及页面内 API Key 验证、保存、测试、更换和移除流程。密钥在服务端加密保存，页面仅显示遮罩。

未配置模型时使用明确标记的规则分析；配置后调用 DeepSeek，失败时显示错误。模型负责分析与建议，自动补菜由确定性规则执行。项目文档注明：真实 DeepSeek 调用尚未联调。

### 数据持久化与模拟隔离

模拟数据与真实数据分别保存到 D1 数据库，共用业务流程但保持来源隔离。真实模式初始没有虚构订单和报损历史，默认关闭自动派单，菜品参数需现场确认后用于自动补菜。

- 测试覆盖跨圈去重、幂等、乱序拒绝、重量噪声、异常恢复、重复任务、闭店补菜、真实完成核对、报损口径及倒计时有效性等场景。
- 已提供运行说明和设备接入文档，并保存桌面端、移动端、经营分析和厨房供菜界面的预览素材。

## 5. 尚待完成与验证的工作

1. **真实设备联调**：连接视觉识别与称重设备，验证盘子标识、采样同步、跨圈追踪及到口预测。
2. **现场规则确认**：校准菜品容量、制作批量、准备时间、目标余量和可信度阈值。
3. **经营数据接入**：收银、采购成本、反馈及会员关联尚未自动接入，当前无法验证真实利润改善。
4. **模型调用联调**：验证真实 DeepSeek 问答、超时及错误处理。
5. **账号与权限**：目前仅拆分岗位视图，尚未实现账号登录、服务端角色授权和按角色裁剪数据。
6. **高频采集扩展**：当前采用按数据来源隔离的状态快照；高频设备接入前需完善事件存储、历史归档和设备在线监测。

统计上，取用量不等于实际吃掉的量，菜品取用排名不代表收入贡献；食材毛利估算未包含人工、租金、能源等完整成本。项目目前处于**首版原型与真实接入准备阶段**，实际减少报损、提高利润的效果仍需门店试运行验证。
